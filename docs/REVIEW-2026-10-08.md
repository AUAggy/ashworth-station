# Ashworth Station review

Reviewed 8 October 2026, against commit `c0fa96a`.

## Verdict

Ashworth Station has a clear identity and a sensible architecture for its job. The station, arriving trains, synthesized sound, and limited ammunition give it more character than a generic browser shooting demo. Static hosting, local saves, and vendored dependencies make it easy to hand someone a link and keep operating it.

Keep that architecture. The next useful work is fixing input and lifecycle bugs, making the menus fit the devices the game targets, and protecting the existing behavior with a small release check. A constrained lighting-and-material pass can then improve visibility and surface quality within the existing renderer. Extra enemies, weapons, rendering passes, or abstractions would deliver less value right now.

The main weakness is inconsistency at the boundaries: a menu gesture becomes a shot, some enemy resources escape cleanup, movement depends on refresh rate, and the new stairwell disagrees with the older flat-world systems.

## What is good

- **The product has a recognizable setting.** Subway typography, platform signage, train doors, eye colors, and station reverb reinforce the same world. Preserve this visual language rather than giving it a generic marketing-site redesign.
- **Deployment is appropriately small.** One application HTML file, two local engine files, and a service worker; no backend, build pipeline, account system, or CDN dependency. The application and engine total roughly 856 KiB before transport compression. The larger social-preview image is not loaded by normal gameplay.
- **The privacy model is straightforward.** Progress stays in browser storage. Authentication and a server-side profile would solve problems this game does not have.
- **Combat has useful feedback.** Enemy windups, directional damage arrows, distinct crawler cues, headshot feedback, and ammo pickups make danger and recovery understandable. The analytic hit volumes and per-type broad-phase bounds are sensible for a small enemy cap.
- **The code contains practical performance work.** Shared prop geometry, instancing, bounded decals and effects, pooled lights, capped resolution, and adaptive pixel ratio all fit the target. Keep the simple enemy loops at the current 30-live-enemy cap unless profiling proves they need replacement.
- **Platform quirks received real attention.** Physical keyboard codes, primary-pointer detection, touch release handling, a reused AudioContext, and containment of sound-effect failures are worthwhile safeguards.
- **The documentation explains decisions.** The bug-history table and tuning tables are useful, specific, and readable. Most rationale comments explain an actual constraint or failure. Deleting them merely to shorten the file would make maintenance worse.

## Graphics assessment

The renderer already has bevelled geometry, procedural textures, normal maps, fog, contact shadows, and reflective materials. Preserve the block-shaped characters and subway identity. Scene screenshots suggest uneven visual emphasis: bright ceiling areas compete with a dark weapon, some surfaces share a similar mottled treatment, and several props need stronger contact shading. These are visual judgments to check in matched before/after views, rather than confirmed rendering defects.

The useful graphics work is better lighting, clearer material differences, and selective geometry adjustment. Keep the existing coarse-pointer budget for the first pass: four pooled lights, a 1.25 pixel-ratio cap, no MSAA, and adaptive resolution. Keep texture sizes and rendering passes unchanged. Runtime-cost estimates below describe expected costs; real phone/tablet performance remains unmeasured.

### 1. Consume the menu gesture

**Evidence:** `index.html:3566–3577` handles desktop fire on window `mousedown`; `index.html:3907–3930` starts the game on the screen's earlier `pointerdown`. The subsequent mouse event sees `playing` and fires. A fresh desktop deploy showed **14 / 120** before any deliberate shot.

Use a desktop shooting `pointerdown` handler on the canvas, with release handled separately, so a gesture that began on the menu cannot also shoot. Check resume and redeploy for the same event-order problem. Avoid another long timeout that also suppresses legitimate shots.

**Done when:** deploy starts at 15 rounds, clicking a difficulty choice does not deploy, and resume/redeploy require a fresh gameplay gesture to shoot.

### 2. Scope service-worker cache cleanup

**Evidence:** `sw.js:24–27` deletes every origin cache except `ashworth-v2`. A mocked activation with `ashworth-v1`, `ashworth-v2`, and `another-game-v9` deleted `another-game-v9`. Cache Storage is shared across an origin; another GitHub Pages project under the same user can be affected despite having a different URL path.

Filter old caches by an Ashworth-specific prefix, then exclude the current version. Look up responses through the game's own cache rather than global `caches.match()`. The runtime cache does not need to grow into a general cache for arbitrary same-origin resources.

**Done when:** activation removes an old Ashworth cache, preserves an unrelated cache, and an offline reload still works. Keep the existing manual cache-version bump rule; add it to the release check.

### 3. Account for every enemy-owned resource

**Evidence:** `index.html:2457–2459` allocates a new jaw geometry and material for each enemy. They are absent from the owned material list at `index.html:2487` and both cleanup paths at `index.html:2629–2632` and `index.html:2797–2800`. Disposal-event checks observed zero jaw disposal events while the listed materials were disposed. Rendered spawn/clear cycles continued increasing the geometry count after initial resource warm-up.

The cheapest fix is to share one jaw geometry and, if its appearance remains static, one jaw material. If a resource really needs to be per-enemy, include it in explicit ownership and cleanup. Do not indiscriminately dispose every descendant: much of the enemy geometry and several materials are intentionally shared.

**Done when:** rendered spawn/death/clear cycles plateau in GPU resource counts after warm-up. Verify natural corpse removal and redeploy separately.

### 4. Fix short-screen menu layout before adding content

**Evidence:** `index.html:99–102` vertically centers an unconstrained panel, while `html,body` prevent scrolling. At 844×390, the menu panel extended from **y = -104 to y = 494**. The title was clipped above the viewport and difficulty controls were below it. The existing narrow-width media query at `index.html:191–198` does not address short landscape screens. Four end-screen statistics also use a fixed 54-pixel gap (`index.html:115`).

Give the screen overlay its own scrollable content area and safe padding, constrain the panel to available height, and add a short-height layout. Reduce title size and instruction spacing there; let end-screen statistics wrap or use a compact grid. Use safe-area insets for controls on notched devices.

**Done when:** deploy, difficulty, resume, and quit remain reachable at 844×390 and 390×844, with no clipped title or statistics. Verify 1024×768 still looks like the current game.

### 5. Apply spawn safety to the landing too

**Evidence:** the stair branch at `index.html:3454–3456` returns before the proximity handling below it. With the player on the landing, a controlled random draw placed a runner only **0.93 meters** away. That is already inside its attack range. The documentation's claim that flanking arrivals never appear close to the player no longer covers this path.

Apply a distance check before accepting every spawn, including the landing. Use a small bounded selection of alternate positions or another existing entrance when none is safe. Preserve the extra pressure on campers without materializing an attacker beside them.

**Done when:** a player standing at each landing position gets an observable approach and reaction window. If the stairwell is closed under item 11, remove this spawn route with it.

### 6. Treat WebGL failure as the end of boot

**Evidence:** `index.html:706–718` supplies a pretend renderer after construction fails. The unconditional PMREM setup at `index.html:739–744` then calls methods that the stub does not have. Forced context failure reproduced the exception after the fallback message rendered.

Show the fallback and stop engine initialization. Do not keep expanding the fake renderer to satisfy more Three.js internals. Keep the error link usable and avoid generating the station's textures and geometry when it cannot render.

**Done when:** forced WebGL failure shows helpful text, produces no uncaught application error, and does not enter the game loop.

### 7. Fix movement at its source

**Evidence:** `index.html:3228–3244` accelerates toward a capped speed and then applies `1 - FRICTION * dt` even while movement input is held. In controlled straight-line tests, steady walking velocity was **2.85 units/s at 30 Hz**, **3.675 units/s at 60 Hz**, and **4.0875 units/s at 120 Hz**. Enemy movement does not apply the same damping. A slower device therefore changes the player's ability to escape.

Separate active movement from stopping friction, or approach the desired velocity with a time-based response. Preserve the intended walking and sprint targets, then revisit balance only if the corrected movement requires it. A physics library or full fixed-step engine is unnecessary for this fix.

**Done when:** equal simulated durations at 30/60/120 Hz produce travel distances within a small agreed tolerance, and release-to-stop, strafing, aiming, and sprinting still feel right.

### 8. Make interruptions safe without changing the challenge blindly

**Evidence:** the three-second pause and ration are deliberate (`index.html:3791–3819`; `README.md:84`). Pointer-lock loss spends that ration. Touch visibility handlers release input (`index.html:3635–3637`) but do not change game state. The pause loop auto-resumes without a gesture, and pointer-lock reacquisition can fail (`index.html:3956–3967`).

The tactical pause is a product choice, not an accidental implementation bug. An OS interruption or unavailable mouse lock is a different condition. Suspend play while hidden/unfocused and require an explicit resume when input is usable again. Consider an ordinary pause on EASY and a separate timed breath on HERO if preserving the ration is important. Add a quit-to-title action during suspension.

**Done when:** app switching, focus loss, and pointer-lock rejection cannot return the player to a live fight without working controls. Make the pause rules visible rather than teaching them through a denied request.

### 9. Add a small release check

Most documented historical bugs and several findings here concern event order, cleanup, and transitions. Manual play remains necessary, but it should not be the only defense against repeating them.

Start with one short checklist and one development-only browser smoke script. Cover deployment without a shot, difficulty changes, weapon/reload behavior, death/redeploy/title transitions, interrupted controls, WebGL failure, viewport fit, and offline reload. Add focused checks for resource disposal, cache isolation, and movement timing as those fixes land. Record the cache bump whenever shipped HTML or engine files change.

Keep tests out of the shipped game. No production build step, framework migration, or elaborate page-object hierarchy is needed. Keep real iPad play on the checklist; Chromium touch emulation cannot replace it. For graphics work, record matched camera views and crowded-wave conditions, actual frame times, draw calls, and GPU resource counts. Measure frame intervals before the simulation's `dt` clamp (`index.html:3933–3939`), and include a sustained real-device session.

**Done when:** a maintainer can check the specific regressions and compare rendering changes against a recorded baseline, without changing how the game is hosted.

### 10. Rebalance lighting before adding effects

**Basis:** existing exposure, environment lighting, and fog are configured at `index.html:721–743`; pooled, ambient, and hemisphere lighting at `index.html:1746–1773`. The scene has useful light sources already, but screenshots show bright ceiling areas and a weapon whose surface detail is difficult to read.

Tune those existing parameters so the weapon, nearby enemies, and platform route remain legible against the darker station. Keep the unsettling mood and colored eye cues. Avoid making the whole room uniformly brighter or hiding crawlers and attack windups in deeper shadows.

**Expected runtime cost:** approximately unchanged when light count, shadow settings, and rendering passes remain fixed. This does not establish unchanged performance on real devices.

**Done when:** matched views show clearer threats and weapon detail at the same resolution, with no material sustained frame-time regression on the target phone/tablet.

### 11. Resolve the stairwell as one feature

The height field works independently, but surrounding systems retain flat-world assumptions:

- The north end wall is still a full bullet-hit plane (`index.html:1542–1546`). A ray from the platform toward the upper stairwell hit that plane at **z = -42.02**. Walking bounds permit passage, while bullets still encounter the wall.
- Pickup creation partly accepts height, but `updatePickups()` overwrites it with a platform-level bob (`index.html:2351–2378`). A drop created at **y = 2.44** moved to **y = 0.182** on its first update. Medkits start at platform height outright.
- Attack and collection range checks are horizontal (`index.html:2688–2709`, `index.html:2380`). Elevation has no explicit role in these checks. This is a source-observed gap; the review did not establish every resulting combat interaction.

**KISS choice:** close the playable stairwell and remove its elevated spawn route for now, leaving the stairs as scenery. If elevation is worth keeping, make an actual opening, preserve each pickup's floor height, and define vertical interaction limits together. Fixing only one subsystem leaves the others inconsistent.

**Done when:** movement, rendering, shots, spawns, attacks, and pickups agree about the same space. This needs a targeted playtest, not a general engine rewrite.

### 12. Give menu actions proper semantics and instructions

**Evidence:** the initial menu has **zero buttons and zero focusable controls**. Deploy and difficulty are divs (`index.html:250–260`), and the screen delegates pointer actions. Touch mode still displays WASD, mouse, and keyboard instructions.

Use styled native buttons for deploy, difficulty, resume, and quit. Provide visible focus, keyboard activation, and an announced selected difficulty. Replace the instruction block on touch devices with the actual controls: left-thumb movement, right-thumb aim, hold-and-drag FIRE, weapon slots, and TURN. Keep detailed lore below the primary action on short screens.

**Done when:** a keyboard user can choose difficulty and start a run, and a first-time tablet player learns the controls from the menu. This does not make a visual FPS fully accessible, but it fixes its accessible surrounding UI.

### 13. Reset transient state explicitly

**Evidence:** `startGame()` at `index.html:3887–3906` resets core stats but leaves aiming/firing, recoil, airborne state, pump state, and bloom untouched. A targeted reset check confirmed they survive when set beforehand. Normal death paths clear some input flags, but do not cover every restart route. Window blur clears keys and firing, but not aiming (`index.html:3602`).

Add a short explicit reset block for these existing fields. Make pointer/touch release and focus-loss paths clear held aim as well as fire. Decide which cosmetic effects intentionally survive a restart; do not let persistence happen by accident.

**Done when:** redeploy during a jump, recoil recovery, or shotgun pump begins from the same baseline as a fresh run, and focus loss cannot leave sights held down.

### 14. Normalize saved data

**Evidence:** `index.html:2952–2960` checks for a badges array but otherwise trusts `ngP` and `best`. A save with `ngP: -5` was accepted. A stored `best.score: null`, followed by a zero-score death, threw while formatting the end screen.

Validate finite, non-negative progression and numeric best-run fields. Use the expected badge count. Drop an invalid best record without discarding valid progress. Build display HTML only from normalized values. No schema library or account system is needed.

**Done when:** missing, malformed, old, negative, and incorrectly typed data either load safely or fall back safely. Storage-disabled play must still work.

### 15. Tune reflective materials using the current shaders

**Basis:** steel and rail materials already distinguish roughness and metalness (`index.html:1271–1275`), and the train has separate body, glass, and door materials (`index.html:1989–1994`). The existing environment map supports highlights without a reflection pass.

Adjust the existing material settings so brushed metal, painted surfaces, glass, and wet patches read differently. Use restrained highlights to show the train and weapon shapes. Keep concrete rough and avoid giving every surface the same glossy finish.

**Expected runtime cost:** approximately unchanged for parameter-only changes on the current materials. Do not add roughness textures, higher-resolution environment maps, or screen-space reflections in this pass.

**Done when:** material differences are visible under the existing lights, without extra texture samplers or rendering passes, and the mobile comparison passes.

### 16. Add a small comfort surface

The audio engine requests a playback session and starts continuous station ambience, but the UI has no mute or volume control (`index.html:313–362`). Reduced-motion CSS only affects the deploy prompt (`index.html:190`), while camera bob, shake, flashes, and badge animation remain.

Add a mute control and a reduced-effects option that cuts camera shake/bob and strong flashes. Persist those preferences locally. Honor reduced-motion preferences by default where practical. Add sensitivity adjustment only if playtesting shows the fixed mouse/touch values are a problem.

**Done when:** a player can silence the game without changing system settings and can reduce visual discomfort without changing combat rules.

### 17. Improve the existing procedural textures

**Basis:** the canvas generators at `index.html:833–1242` already provide tile grids, directional train-metal strokes, cracks, stains, and skin detail. Some surfaces in the screenshots share a similar mottled appearance despite representing different materials.

Strengthen the useful patterns: readable grout at gameplay distance, directional wear on metal, and broader stains on concrete. Reduce uniform fine noise where it hides the surface underneath. Preserve the existing texture dimensions and reuse. Check the derived normal maps too, so stronger painted detail does not accidentally produce exaggerated relief.

**Expected runtime cost:** similar GPU cost at unchanged texture sizes, material features, and sampler counts. More generation work can increase startup time; measure it. A normal map generated at boot still adds texture sampling and shading work every rendered frame.

**Done when:** tile, metal, concrete, and skin remain distinct at mobile resolution without extra textures, expanded normal-map coverage, or a material startup/performance regression.

### 18. Give objects weight with existing contact shading

**Basis:** the station already generates a contact-shadow texture (`index.html:1132–1141`) and uses it on props and enemies. This provides a low-cost foundation for grounding objects without a full-screen ambient-occlusion pass.

Adjust existing contact-shadow placement, scale, and opacity where objects appear detached. Paint subtle seam and edge darkening into existing static-surface textures where their mapping supports it. Retain movable shadow proxies for enemies; painted shading must not imply a fixed shadow under a moving object. Avoid adding layers of transparent quads throughout the station.

**Expected runtime cost:** little additional runtime work if texture sizes, shadow meshes, and draw-call counts stay unchanged. Poorly sized transparent shadows can still increase overdraw.

**Done when:** benches, columns, and enemies sit convincingly on their surfaces, shading does not float or clip, and draw calls and sustained mobile frame times stay within the baseline.

### 19. Correct small drift, then stop polishing

Useful low-cost corrections:

- `README.md:11–20` initially suggests downloading one HTML file, while the later hosting section correctly requires `vendor/` and `sw.js`. Put the complete copy/run instructions first. Distinguish local offline serving from a hosted page that needs an initial service-worker installation.
- `README.md:144` says a sixth badge is supported, but the initial badge array, load loop, and displayed denominator assume five (`index.html:2949–2973`). Correct the claim unless adding a sixth badge is an actual requirement.
- The promise that the record measures survival time (`README.md:3`) differs from `recordRun()` comparing score only (`index.html:3824–3828`). Choose one primary record and make the copy match it. Rename end-screen "WAVES HELD" to "WAVE REACHED" if it continues displaying the current wave, including a wave lost before completion.
- Record the source/version and license of the vendored engine. Its revision is pinned, but provenance is not documented beside the files. No specific dependency vulnerability was established in this review.
- Remove proven unused fields such as `_tmpQ`, `reloadStage`, and `shellBig` after checking references. Avoid a mass renaming or formatting pass.
- Remove the redundant non-indexed conversion in `chamferBox()` only after verifying geometry and ownership behavior. It currently produces repeated startup warnings; the warning count is evidence of cleanup work, not evidence that rendering is broken.

One additional source-observed balance edge deserves a focused check: `buildComposition()` can exceed the requested EASY final-wave count at NG+ levels, while `wave.queue` remains `n` (`index.html:3400–3427`). Randomly shuffled excess entries are then unused. Preserve the intended EASY difficulty while making the recipe and queue agree.

### 20. Refine silhouettes selectively

**Basis:** enemy shapes and poses are built at `index.html:2402–2488`; weapon shapes at `index.html:2817–2884`. The block-shaped style is part of the game's identity. Small adjustments to proportions, existing bevels, and poses can improve recognition without replacing those models.

Prioritize the weapon, which occupies a large part of the view, and the enemy poses that communicate an approach or windup. Reshape existing parts before adding meshes. Avoid spending polygons on distant details that disappear at mobile resolution. Preserve analytic hit volumes, aim-assist targets, and muzzle/ejection positions, or update and test them together with the visible model.

**Expected runtime cost:** low for adjustments that retain current mesh and triangle counts. Additional geometry needs measurement, even when it looks inexpensive compared with a full-screen effect.

**Done when:** weapons and enemy types are easier to recognize, telegraphs remain clear, hit detection still matches the silhouettes, and geometry/draw-call budgets pass the mobile comparison.

## Graphics performance guardrails

Defer multi-light real-time shadows, SSAO, depth of field, motion blur, screen-space reflections, higher render resolution, and more dynamic lights. These can add scene renders, full-screen passes, or per-fragment work. Large smoke/glow layers can add substantial overdraw. None is required for the first graphics pass.

Use the baseline from item 9 and change one visual subsystem at a time. Compare the same camera views and crowded-wave conditions at the same resolution and quality settings. Inspect actual frame times, draw calls, resource counts, and startup time, then check sustained performance on the target phone or iPad. A prettier screenshot or short desktop preview cannot establish mobile safety. Do not raise resolution to conceal a weak material or reduce resolution to conceal the cost of an added effect.

## KISS boundaries

Keep the single application file while its section boundaries remain useful. A 4,008-line file is a navigation cost, but length alone does not justify a framework or dozens of modules. If one subsystem becomes difficult to change safely, extract that whole subsystem with a small interface rather than splitting every helper into a separate file.

Do not add an ECS, generalized event bus, dependency-injection framework, physics engine, backend leaderboard, accounts, telemetry, or remote asset pipeline to address these findings. Do not replace bounded loops and pools with more elaborate structures without measurements. Do not build a configurable badge/plugin system for a hypothetical sixth badge.

## Suggested first pass

Fix items **1–4** first: consume deployment input, scope cache deletion, account for jaw resources, and make menus fit. They address confirmed defects with limited changes and preserve the game's identity. Add their checks immediately rather than postponing all testing until item 9.

Then address spawn fairness and movement consistency, and make a deliberate keep-or-close decision on the stairwell before adding another feature. Establish the rendering baseline in item 9 before graphics changes. Start the visual pass with lighting and existing material settings (items **10 and 15**); expand to textures, contact shading, and silhouettes (items **17–18 and 20**) only after those changes pass the mobile comparison. Leave broad refactoring and heavier effects until the behavior and performance are stable.
